# Задача для Codex: добавить страницу “Дашборд” со сводным отчетом по площадям и динамикой по месяцам

## Контекст

В сервис аналитики предложений застройщиков нужно добавить новый отчет, который раньше собирался вручную.

Отчет должен стать отдельной страницей в сервисе.

Название раздела в навигации:

```text
Дашборд
```

Название внутренней страницы:

```text
Сводный отчет по площадям
```

Важно: не нужно создавать отдельные страницы по каждому застройщику. Нужна только одна сводная страница, где все застройщики сравниваются в общей таблице, визуализациях и динамике.

---

# 1. Цель отчета

Нужно сделать страницу, которая отвечает на вопрос:

```text
Сколько квартир и на какую сумму представлено у каждого застройщика в разных диапазонах площади?
```

Отчет должен показывать структуру предложения по диапазонам площади:

- по количеству квартир;
- по сумме стоимости квартир;
- по каждому застройщику;
- по рынку в целом;
- отдельно с возможностью сравнить КССК с конкурентами;
- в текущем срезе;
- в динамике по месяцам.

Ключевое требование: отчет должен сохранять историю и позволять смотреть динамику минимум по месяцам.

---

# 2. Где разместить отчет

Добавить новый раздел в основную навигацию:

```text
Дашборд
```

Рекомендуемый URL:

```text
/dashboard
```

или:

```text

```

Заголовок страницы:

```text

```

```text
Обзор рынка | Сравнение с КССК | Застройщики | Планировки | Динамика | Дашборд
```

Если в сервисе уже есть новая структура навигации, встроить `Дашборд` в нее.

---

# 3. Источник данных

Отчет должен строиться из текущих данных сервиса, а не из отдельного файла.

Использовать уже существующие сущности:

```text
Developer
Project
Building
Apartment
Snapshot
ApartmentSnapshot
LayoutGroup
```

Если в сервисе есть актуальный срез квартир, отчет должен строиться по нему.

По умолчанию в отчет включать только квартиры в продаже.

Если в проекте есть внутренний статус активной квартиры, использовать текущую логику сервиса. Если нет, использовать:

```ts
status === "available"
```

Если статус неизвестен, но квартира присутствует в актуальном срезе, ее можно считать активной, если такая логика уже используется в других отчетах.

---

# 4. История и динамика отчета

Важно: отчет не должен быть только статичным срезом на текущую дату.

Нужно сохранять историю данных, чтобы можно было смотреть динамику показателей минимум по месяцам.

---

## 4.1. Сохранение исторических срезов

При каждом обновлении данных нужно сохранять отдельный срез.

Использовать существующую модель:

```text
Snapshot
ApartmentSnapshot
```

Если этих сущностей недостаточно, доработать их так, чтобы можно было восстановить состояние предложения на конкретную дату.

Для каждого среза сохранять:

```text
snapshot_id
snapshot_date
source
developer_id
project_id
apartments_count
total_sum
created_at
```

Для каждой квартиры в срезе сохранять:

```text
snapshot_id
apartment_id
developer_id
project_id
building_id
rooms
area
price
price_per_sqm
status
layout_group_id
created_at
```

Важно: при обновлении данных не удалять старые квартиры и старые срезы.

---

## 4.2. Месячная динамика

На странице `Дашборд / Сводный отчет по площадям` добавить возможность смотреть отчет в двух режимах:

```text
Текущий срез
По месяцам
```

В режиме `По месяцам` отчет должен агрегировать данные по месяцам.

Для каждого месяца считать:

- количество квартир;
- сумма предложения;
- количество квартир по диапазонам площади;
- сумма предложения по диапазонам площади;
- количество квартир по застройщикам;
- сумма предложения по застройщикам;
- доля КССК по количеству;
- доля КССК по сумме;
- изменение к предыдущему месяцу.

---

## 4.3. Логика месячного среза

Для каждого месяца использовать последний доступный срез внутри месяца.

Например:

```text
Январь 2026 -> последний срез за январь
Февраль 2026 -> последний срез за февраль
Март 2026 -> последний срез за март
```

Если в месяце нет срезов, месяц можно пропустить или показать как `нет данных`.

Не нужно суммировать все срезы месяца между собой, иначе квартиры будут задвоены. Для месячной динамики нужен именно последний срез месяца.

Если выбран период, для статичного отчета использовать последний доступный срез внутри выбранного периода. Для режима динамики агрегировать данные по месяцам, используя последний доступный срез каждого месяца.

---

## 4.4. Показатели динамики

Для каждого месяца и каждого диапазона площади считать:

```text
area_range
month
apartments_count
total_sum
```

Также считать изменения к предыдущему месяцу:

```ts
count_change = current_month_count - previous_month_count
count_change_pct = ((current_month_count - previous_month_count) / previous_month_count) * 100

sum_change = current_month_sum - previous_month_sum
sum_change_pct = ((current_month_sum - previous_month_sum) / previous_month_sum) * 100
```

Если в предыдущем месяце значение равно 0 или отсутствует, процент изменения не считать и показывать `н/д`.

# 5. Участники отчета

Отчет должен поддерживать любое количество застройщиков из базы.

В текущей логике ожидаются такие участники рынка:

```text
КССК
Железно
КСМ
Маяковская
УКС Авитек
СМУ5
СтройСоюз
КИНО девелопмент
ПрофСтрой
Алтай-Строй
Сретенский посад
ПС Недвижимость
```

Но список нельзя хардкодить только этими названиями. Нужно строить отчет динамически по всем застройщикам, которые есть в базе и попадают под выбранные фильтры.

КССК должен определяться как собственная компания:

```ts
developer.type === "own"
```

Конкуренты:

```ts
developer.type === "competitor"
```

# 6. Диапазоны площади

Использовать фиксированные диапазоны площади:

```text
до 30,9 кв.м
31–40,9 кв.м
41–50,9 кв.м
51–60,9 кв.м
61–70,9 кв.м
71–80,9 кв.м
81–90,9 кв.м
свыше 91 кв.м
```

Техническая логика:

```ts
area <= 30.9                           -> "до 30,9 кв.м"
area >= 31 && area <= 40.9             -> "31–40,9 кв.м"
area >= 41 && area <= 50.9             -> "41–50,9 кв.м"
area >= 51 && area <= 60.9             -> "51–60,9 кв.м"
area >= 61 && area <= 70.9             -> "61–70,9 кв.м"
area >= 71 && area <= 80.9             -> "71–80,9 кв.м"
area >= 81 && area <= 90.9             -> "81–90,9 кв.м"
area >= 91                             -> "свыше 91 кв.м"
```

Если площадь отсутствует или не распознана, квартира не должна попадать в диапазоны.

При этом на странице нужно показывать предупреждение:

```text
Есть квартиры без площади: {count}
```

# 7. Основные показатели

Для каждого застройщика и каждого диапазона площади нужно считать:

## 7.1. Количество квартир

Если каждая квартира хранится отдельной записью:

```ts
count = number of apartments
```

Если источник содержит агрегированную строку с количеством квартир, учитывать поле количества:

```ts
count = sum(apartment_count)
```

Если агрегированных данных нет, считать каждую запись как одну квартиру.

---

## 7.2. Сумма стоимости квартир

Если каждая квартира хранится отдельной записью:

```ts
sum = sum(price)
```

Если есть агрегированное количество:

```ts
sum = sum(price * apartment_count)
```

Если есть готовое поле полной стоимости:

```ts
sum = sum(total_price)
```

Если цена отсутствует, квартира должна входить в количество, но не должна входить в сумму стоимости.

Показать предупреждение:

```text
Есть квартиры без цены: {count}
```

---

## 7.3. Итого по застройщику

Для каждого застройщика считать:

```ts
developer_total_count = sum(count across all area ranges)
developer_total_sum = sum(sum across all area ranges)
```

---

## 7.4. Итого по рынку

По всем застройщикам считать:

```ts
market_total_count = sum(developer_total_count)
market_total_sum = sum(developer_total_sum)
```

# 13. Ключевые выводы

Добавить блок автоинсайтов:

```text
Ключевые выводы
```

Инсайты должны строиться по правилам.

## 13.1. Самый массовый диапазон КССК

```text
У КССК больше всего квартир в диапазоне {range}: {count} квартир.
```

## 13.2. Самый массовый диапазон рынка

```text
На рынке самый массовый диапазон — {range}: {count} квартир.
```

## 13.3. КССК недопредставлен в диапазоне

Если доля КССК в диапазоне ниже общей доли КССК по рынку более чем на 10 п.п.:

```text
КССК недопредставлен в диапазоне {range}: доля {range_share}% против общей доли {overall_share}%.
```

## 13.4. КССК сильно представлен в диапазоне

Если доля КССК в диапазоне выше общей доли КССК по рынку более чем на 10 п.п.:

```text
КССК сильнее представлен в диапазоне {range}: доля {range_share}% против общей доли {overall_share}%.
```

## 13.5. Максимальная сумма предложения КССК

```text
Наибольшая сумма предложения КССК приходится на диапазон {range}: {sum} ₽.
```

## 13.6. Отличие от конкурентов

```text
В диапазоне {range} КССК занимает {share}% предложения по количеству квартир.
```

## 13.7. Нулевое присутствие КССК

Если в диапазоне у конкурентов есть квартиры, а у КССК 0:

```text
У КССК нет предложения в диапазоне {range}, при этом у конкурентов в нем {competitor_count} квартир.
```

# 15. Логика фильтров

- Если выбран конкретный застройщик, таблица показывает только его.
- Если выбран режим `КССК + конкуренты`, показывать всех.
- Если выбран режим `Только конкуренты`, исключать КССК.
- Если выбран режим `Только КССК`, показывать только КССК.
- Если выбрана комнатность, пересчитывать отчет только по этой комнатности.
- Если выбран проект, пересчитывать только по выбранному проекту.
- Если выбран период, для статичного отчета использовать последний доступный срез внутри выбранного периода.
- Если выбран режим `По месяцам`, агрегировать данные по месяцам, используя последний доступный срез каждого месяца.

# 18. Таблица и горизонтальный скролл

Так как застройщиков может быть много, основная сводная таблица будет широкой.

Требования:

- обернуть таблицу в контейнер с горизонтальным скроллом;
- первую колонку `Диапазон площади` желательно сделать sticky;
- строку `ИТОГО` визуально выделить;
- числовые колонки выровнять вправо;
- суммы форматировать в рублях;
- пустые значения показывать как `0`, если в диапазоне нет квартир.

# 19. Empty states и предупреждения

Если нет данных:

```text
Нет данных для построения отчета.
```

Если нет данных по выбранным фильтрам:

```text
Нет данных для выбранных фильтров.
```

Если есть квартиры без площади:

```text
{count} квартир не попали в отчет, потому что у них не указана площадь.
```

Если есть квартиры без цены:

```text
{count} квартир не попали в расчет суммы, потому что у них не указана цена.
```

Если нет КССК в данных:

```text
Данные КССК не найдены. Сравнение КССК с конкурентами недоступно.
```

Если нет конкурентов:

```text
Данные конкурентов не найдены. Сравнение КССК с рынком недоступно.
```

Если есть только один срез и динамику посчитать нельзя:

```text
Недостаточно истории для расчета динамики. Динамика появится после накопления нескольких срезов.
```

Если нет срезов за выбранный период:

```text
Нет данных за выбранный период.
```

# 23. Критерии готовности

Функционал считается готовым, если:

1. Добавлена отдельная страница `Дашборд`.
2. Внутренняя страница называется `Сводный отчет по площадям`.
3. Нет отдельных страниц по каждому застройщику.
4. Отчет строится по текущим данным сервиса.
5. История срезов сохраняется и не затирается.
6. Можно смотреть отчет в режиме текущего среза.
7. Можно смотреть динамику по месяцам.
8. Для месяца используется последний доступный срез внутри месяца.
9. Используются фиксированные диапазоны площади.
10. По каждому застройщику считается количество квартир и сумма стоимости.
11. Есть строка `ИТОГО`.
12. Есть KPI сверху.
13. Есть сравнение КССК vs конкуренты.
14. Есть график количества по диапазонам.
15. Есть график суммы по диапазонам.
16. Есть графики динамики по месяцам.
17. Есть ключевые выводы.
18. Есть инсайты по динамике.
19. Есть фильтры.
20. Есть экспорт основной сводки.
21. Есть экспорт месячной динамики.
22. Есть empty states и предупреждения.
23. Основные расчеты покрыты тестами.
24. Линтер, тесты и сборка проходят успешно.
