# Задача для Codex: реализовать страницу “КССК vs рынок” и сбор данных КССК с сайта

## Контекст

Мы разрабатываем внутренний сервис аналитики планировочных решений застройщиков.

Сейчас в сервисе уже есть:

- общая страница рынка;
- аналитика застройщика;
- анализ вариативности планировок;
- страница всех планировок;
- карточки типовых планировок;
- метрики по проектам, домам, комнатности, ценам, площадям и динамике;
- сбор данных по конкурентам.

Сейчас в сервисе есть данные по конкурентам. Нужно добавить данные нашей компании — **КССК** — и реализовать отдельную страницу сравнения:

```text
КССК vs рынок
```

Главная цель сервиса — не просто анализировать конкурентов, а сравнивать **наше предложение КССК** с предложениями конкурентов и понимать:

- где КССК дороже или дешевле рынка;
- где у КССК выше или ниже чек входа;
- где у КССК больше или меньше площадь;
- где КССК недопредставлен по комнатности;
- где у конкурентов есть форматы, которых нет у КССК;
- где у КССК сильные стороны;
- где есть риски;
- какие продуктовые ниши можно рассмотреть для будущих проектов.

Текущую страницу **“Рынок”** нужно сохранить как отдельную страницу общего рыночного обзора. Новая страница должна быть отдельной и сфокусированной именно на сравнении КССК с конкурентами.

---

# 1. Главная логика

## 1.1. КССК — это отдельный тип участника рынка

Не нужно создавать отдельную модель “наши предложения”.

КССК должен храниться в той же модели данных, что и конкуренты:

- Developer / Застройщик;
- Project / Проект;
- Building / Дом;
- Apartment / Квартира;
- LayoutGroup / Типовая планировка;
- Snapshot / Срез;
- ApartmentSnapshot / Состояние квартиры в срезе.

Нужно добавить признак, который отличает нашу компанию от конкурентов.

Предпочтительный вариант:

```ts
developer.type = "own" | "competitor"
```

Для КССК:

```ts
{
  name: "КССК",
  type: "own"
}
```

Для всех остальных застройщиков:

```ts
{
  type: "competitor"
}
```

Если в текущей модели проще добавить boolean, можно использовать:

```ts
developer.isOwnCompany = boolean
```

Но предпочтительнее `type: "own" | "competitor"`.

---

## 1.2. Не смешивать КССК и рынок конкурентов

На странице **“КССК vs рынок”** все сравнения должны строиться так:

```text
КССК = developer.type === "own"
Рынок конкурентов = developer.type === "competitor"
```

Важно:

- КССК не должен попадать в расчет медианы рынка конкурентов.
- КССК не должен попадать в расчет средних значений рынка конкурентов.
- КССК не должен искажать структуру комнатности рынка.
- КССК должен сравниваться именно с конкурентами, а не со смешанной выборкой.

# 2. Источник данных КССК

## 2.1. Основной источник для MVP

На первом этапе данные КССК нужно получать с публичного сайта:

```text
https://kvartiry.kssk.ru/
```

На этом сайте находится общий каталог квартир КССК. Внутри по каждому проекту могут быть отдельные сайты или страницы проектов.

Нужно реализовать сбор данных КССК с этого сайта и привести их к той же модели данных, что используется для конкурентов.

Тип источника:

```ts
source.type = "kssk_site"
```

КССК должен храниться как наша компания:

```ts
developer.name = "КССК"
developer.type = "own"
```

---

## 2.2. Что нужно собрать с сайта

Для каждой квартиры КССК нужно по возможности получить:

```text
developer
project
building
apartment_code
rooms
area
floor
price
price_per_sqm
status
source_url
layout_image_url
layout_group_id / layout_hash, если возможно
```

Где:

- `developer` всегда `КССК`;
- `project` — название проекта;
- `building` — дом / корпус / очередь, если есть;
- `apartment_code` — уникальный код или номер квартиры;
- `rooms` — комнатность;
- `area` — площадь;
- `floor` — этаж;
- `price` — цена квартиры;
- `price_per_sqm` — цена за м², если есть на сайте, иначе считать;
- `status` — статус квартиры, если есть;
- `source_url` — ссылка на карточку квартиры или страницу, откуда она получена;
- `layout_image_url` — ссылка на изображение планировки, если есть.

Если часть полей отсутствует, сохранять то, что удалось получить, но не ломать сбор.

---

## 2.3. Логика обхода сайта

Нужно изучить структуру сайта:

```text
https://kvartiry.kssk.ru/
```

Реализовать сбор так, чтобы он мог:

1. Открыть общий каталог квартир КССК.
2. Найти список проектов или ссылки на сайты/страницы проектов.
3. Перейти по каждому проекту.
4. Собрать список квартир.
5. Для каждой квартиры получить доступные параметры.
6. Сохранить данные в текущую базу сервиса.
7. Создать новый Snapshot.
8. Создать ApartmentSnapshot для каждой найденной квартиры.
9. Обновить `first_seen_at` и `last_seen_at`.
10. Пометить квартиры, которые были раньше, но не найдены в новом сборе, как `gone_from_exposure`.

Важно: если сайт использует динамическую загрузку данных через API, нужно найти этот API в network-запросах и использовать его напрямую, если это проще и надежнее, чем парсинг HTML.

---

## 2.4. Приоритет источника данных на сайте

Предпочтительный порядок:

1. Использовать публичный JSON/API сайта, если он есть.
2. Если API нет — парсить HTML.
3. Если контент рендерится JavaScript-ом — использовать текущий подход проекта для динамических сайтов, например Playwright/Puppeteer, если они уже есть в проекте.
4. Если в проекте нет браузерного парсера, не добавлять тяжелую зависимость без необходимости. Сначала попробовать найти API.

# 3. Нормализация данных КССК

Все значения нужно привести к единому формату, который уже используется в сервисе.

## 3.1. Цена

Примеры возможного входа:

```text
9 290 840 ₽
9290840
9.29 млн ₽
```

Сохранять как число:

```ts
price: number
```

## 3.2. Площадь

Примеры возможного входа:

```text
59.1 м²
59,1
59.1
```

Сохранять как число:

```ts
area: number
```

## 3.3. Цена за м²

Если на сайте нет цены за м², считать автоматически:

```ts
price_per_sqm = price / area
```

Если `area` отсутствует или равна 0, не считать цену за м² и сохранять `null`.

## 3.4. Комнатность

Нормализовать к текущему формату сервиса:

```text
Студия
1
1+
2
2+
3
3+
4+
```

Если на сайте используются другие обозначения, добавить mapping.

Например:

```ts
{
  "студия": "Студия",
  "studio": "Студия",
  "1-комн": "1",
  "1-комнатная": "1",
  "1+": "1+",
  "2-комн": "2",
  "2+": "2+",
  "3-комн": "3",
  "3+": "3+"
}
```

## 3.5. Статус

Если на сайте есть статусы, привести к внутренним:

```ts
status:
  | "available"
  | "reserved"
  | "sold"
  | "gone_from_exposure"
  | "unknown"
```

Если статус отсутствует, но квартира есть в выдаче:

```ts
status = "available"
```

Важно: если квартира исчезла из сайта, не считать ее проданной без явного статуса `sold`.

Использовать формулировку:

```text
ушла из экспозиции
```

# 4. Уникальность квартиры

Нужно определить стабильный уникальный ключ квартиры.

Приоритет:

1. ID квартиры с сайта, если есть.
2. Код квартиры с сайта.
3. Ссылка на карточку квартиры.
4. Комбинация:

```text

```

Сохранить этот ключ в поле:

```ts

```

# 5. Снимки и история

При каждом обновлении данных КССК:

1. Создать новый `Snapshot` с источником `kssk_site`.
2. Сохранить все найденные квартиры в `ApartmentSnapshot`.
3. Для новых квартир проставить `first_seen_at`.
4. Для найденных квартир обновить `last_seen_at`.
5. Если квартира была в предыдущем срезе КССК, но не найдена сейчас, не удалять ее.
6. Для отсутствующих квартир поставить статус:

```ts
gone_from_exposure
```

Не называть такие квартиры проданными, если сайт явно не дает статус `sold`.

# 6. Группировка типовых планировок КССК

Если у квартир есть изображения планировок, нужно использовать их для группировки в `LayoutGroup`.

MVP-логика:

1. Если есть `layout_image_url`, использовать его как базу для группировки.
2. Если есть возможность посчитать `image_hash` или `layout_hash`, использовать его.
3. Если хэша пока нет, временно группировать по:

```text
project + building + rooms + area + layout_image_url
```

Если изображения планировок нет, квартира все равно должна попадать в аналитику, но может быть без `layout_group_id`.

# 13. Блок “Главные отличия КССК”

Добавить блок автоинсайтов.

Название:

```text
Главные отличия КССК
```

Инсайты должны объяснять, что значит разница в данных, а не просто повторять цифры.

Примеры правил:

## 13.1. Если КССК дороже рынка по цене за м²

```text
КССК дороже рынка по цене за м² на {diff}%. Проверьте, оправдана ли разница площадью, локацией или качеством планировок.
```

## 13.2. Если КССК дешевле рынка по цене за м²

```text
КССК дешевле рынка по цене за м² на {diff}%. Это может быть ценовым преимуществом в выбранной выборке.
```

## 13.3. Если площадь КССК выше рынка

```text
Медианная площадь квартир КССК выше рынка на {diff_m2} м². Это может повышать комфорт продукта, но также увеличивает общий чек.
```

## 13.4. Если площадь КССК ниже рынка

```text
Медианная площадь квартир КССК ниже рынка на {diff_m2} м². Это может снижать чек входа, но продукт может выглядеть компактнее конкурентов.
```

## 13.5. Если доля комнатности ниже рынка

```text
В сегменте {rooms} доля КССК ниже рынка на {diff_pp} п.п. Проверьте, не теряем ли мы спрос в этом формате.
```

## 13.6. Если доля комнатности выше рынка

```text
КССК сильнее представлен в сегменте {rooms}: доля выше рынка на {diff_pp} п.п.
```

## 13.7. Если КССК более стандартизирован

```text
КССК более стандартизирован, чем рынок: {own_value} кв./план. против {market_value}. Это может говорить о лучшей типизации, но меньшем выборе для покупателя.
```

## 13.8. Если КССК более вариативен

```text
КССК более вариативен, чем рынок: {own_value} кв./план. против {market_value}. Это дает покупателю больше выбора, но может усложнять стандартизацию продуктовой матрицы.
```

# 19. Блок “Продуктовые ниши”

Добавить автоматический поиск ниш.

Ниша — это сегмент, где у конкурентов есть предложение, а у КССК предложения нет или сильно меньше.

Сегменты для MVP:

```text

```

```text

40–50 м²
50–60 м²
60–70 м²
70–85 м²
85–100 м²
100+ м²
```

Для каждого сегмента считать:

- квартир у конкурентов;
- доля КССК;
- доля рынка;
- разница;
- медианная цена рынка;

Примеры ниш:

```text

3+ до 85 м²: у конкурентов 11 квартир, у КССК 0.
```

Правила:

- если у конкурентов >= 5 квартир в сегменте, а у КССК 0 — показать как “нет предложения”;
- если доля КССК ниже рынка более чем на 10 п.п. — показать как “слабое присутствие”;
- если сегмент активно уходит из экспозиции у конкурентов, помечать как “потенциально ликвидный”, если есть история.

# 23. Формулы и расчеты

## 23.1. Разница в процентах

```ts
diffPct = ((ownValue - marketValue) / marketValue) * 100
```

Если `marketValue` равен 0 или отсутствует — не считать процент, показывать `н/д`.

## 23.2. Разница в процентных пунктах

Для долей:

```ts
diffPp = ownShare - marketShare
```

Например:

```text
КССК 18%, рынок 27%, разница -9 п.п.
```

## 23.3. Квартир на планировку

```ts
apartmentsPerLayout = apartmentsCount / layoutGroupsCount
```

Если `layoutGroupsCount` равен 0, показывать `н/д`.

## 23.4. HHI по планировкам

```ts
HHI = sum((apartmentsInLayout / totalApartments) ** 2)
```

Показывать в формате 0–1.

## 23.5. Минимальный чек входа

```ts
minEntryPrice = min(price) by rooms_normalized
```

## 23.6. Медианы

Для цен, площади и цены за м² использовать медиану, а не только среднее.

Средние значения можно показывать дополнительно.

# 29. Важные продуктовые правила

## 29.1. Не смешивать КССК и рынок конкурентов

В сравнительной аналитике рынок = только конкуренты.

КССК не должен попадать в расчет медианы рынка конкурентов.

## 29.2. Не называть исчезнувшие квартиры продажами

Если квартира исчезла из выдачи, использовать:

```text
ушла из экспозиции
```

Не использовать:

```text
продана
```

если нет явного статуса продажи.

## 29.3. Использовать медианы

Для сравнения цен, площади и цены за м² использовать медианы как основные показатели.

Средние можно показывать дополнительно.

## 29.4. Не делать автоматических категоричных выводов

Например, если КССК дороже рынка, не писать автоматически “это плохо”.

Лучше:

```text
КССК дороже рынка по цене за м² на 5.3%. Проверьте, оправдана ли разница площадью, локацией или качеством планировок.
```
